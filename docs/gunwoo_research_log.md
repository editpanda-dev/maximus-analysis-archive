## 1. 용인 글로벌캠퍼스 확장 (2026-10-29 ~ 10-31)

### 요약
**목적**: 2026 AI 캠퍼스 바이브코딩 경진대회용. 막시무스의 동대문 상권 랭킹 방법을 한국외대 글로벌캠퍼스(용인 모현) 출발로 다시 만들었다. 같은 방법을 서울캠퍼스 출발에도 적용했다. 기획서 마감은 11-10이다.

**만든 것**
- 모현 출발 대중교통 30분 도달 모형: GBIS 노선망 정적 모형, ODsay 실측 13곳으로 보정(평균오차 3.1분)

**핵심 발견**
- 30분 생활권은 모현읍과 오포뿐이다. 12km 안 점포 14,645곳 중 1,495곳(10%)만 든다.

**상태**: 검증 전. '숨은 곳'과 '30분 도달'을 둘 다 아직 증명하지 못했다. 서울캠 ODsay 측정은 하루 30건 한도로 89/773건에서 멈춰 있다.

### 1.4 발견
1. **30분 생활권은 모현읍과 오포뿐이다.** 경안동(경기광주역), 분당, 용인 시내는 모두 38분 이상 걸린다.
2. **주변에 아무것도 없다는 게 데이터로 확인된다.** 30분 안 관광·문화 명소는 캠퍼스 안 2곳(노천극장, 명수당)과 모멘토리아트홀뿐이다. 나머지 36곳은 체육시설과 공원이다. 곤지암루지·화담숲은 직선 1.7~2km지만 걸으면 4시간이다.
3. **숨은 가치는 상권 안에 있다.** 오포 양벌·매산·문형에 노포(들밥, 막끌리네, 캠핑7, 고래성 등)가 몰려 있다. 개인 로스터리와 수상레저·실내낚시·볼링 같은 드문 여가도 있다.
4. **외부 검증 신호는 약하다.** 30분 안 TourAPI 소개 음식점 3곳이 모두 숨은 가게 목록에 있었다(3/3). 표본이 작고, 이미 알려진 곳이라는 반증일 수도 있다.
5. **오포가 새로 갈 곳이다.** 오포2동 양벌로(#34)는 쇼핑 76, 카페 92로 30분 안 1위이고 20.8분 걸린다.
6. **셔틀로 새로 열리는 30분 상권은 없다.** 하교편은 판교·서현 노선뿐이고 45~50분 걸린다. 돌아오는 편도 없다.
7. **45분 확장 단계에서 관광공사 소개 노포가 나온다.** 포곡읍, 경안동, 광남1동, 능평, 신현으로 넓어지고 장지리막국수, 추자리막국수, 장지한우, 두부마당이 나온다.

### 1.5 민감도
- 군집 반경(60·100·150m)과 최소 점포(10·20·30·50)를 바꾸면 30분 안 상권 수가 6~25곳(대기 없음), 2~13곳(대기 포함)으로 흔들린다.
- 식사 상위 3곳은 24개 조합 대부분에서 유지된다(3/3, 일부 2/3). 상위는 안정적이고 개수는 불안정하다.
- 노포 수는 상호 유사도(0.5~0.7)에 둔감하고(103~105곳) 기준연도에 비례한다(2000년 77, 2005년 103, 2010년 134).

### 1.6 서울캠퍼스

## 2. 의외성(세렌디피티) 상권 추천 SERP (2026-11-02)

### 요약
**목적**: "늘 가던 곳(관성)과 다르지만 갈 만한 상권"을 추천한다. 동대문구 출발 30분 후보 786곳, 목적은 식사·카페·쇼핑·여가문화·공부다.

**로직**
- 관련성 R: 구조 변수 Ridge로 예측한 목적 매출 백분위(0.8) + 30분 도달률(0.2)
- 의외성 U: 저유입 잔차 + 새로움(비인기) + 업종 구성 거리 + 공간 거리
- 점수 S = R × U. R이 목적 안 하위 60%이면 추천에서 뺀다. MMR(λ=0.7)로 다양성을 맞춘다.
- 관성 기준선 3개: 거리순, 인기순, 과거 유입순

**v1 재설계**: 공간 거리 가점을 없앴다. 관성 상권은 아예 제외하고, 이동시간 구간(≤15분, 15~22분, 22~30분)마다 3곳씩 고른다. 서울캠 출발 옵션을 추가했다.

**검증**: 정답 라벨이 없어 정확도는 주장하지 않는다. 대신 프록시 라벨 백테스트, beyond-accuracy 지표, 반사실 시뮬레이션, 민감도를 돌렸다. 라벨은 Kotkov식 3문항 설문으로 확보할 계획이다.

**상태**: 코드·테스트·결과 커밋 완료. 동대문구발 실제 OD(B078)가 없어 유입 관련 항은 프록시다.

**문서**: `[serendipity] docs/serendipity/recommendation_design.md`, 코드 `scripts/build_serendipity_ranking.py`, 결과 `data/processed/serendipity_ranking/`

### 2.1 관성 기준선
| 기준선 | 정의 |
|---|---|
| 거리순 | 동대문구 상권 중심점에서의 직선거리 오름차순 |
| 인기순 | 직전 분기 목적 매출 내림차순(공부는 목적 점포 수) |
| 과거 유입순 | 비일상 유입 × 동대문구 30분 도달률. 동대문구발 OD가 아닌 프록시다 |

관성 Top-K(K=10)는 세 목록 상위 10곳의 합집합이다.

### 2.2 점수
- `R = 백분위(0.8 × r_attract + 0.2 × r_access)`
  - `r_attract`: 총 점포 수, 면적, 업종 엔트로피, 목적 점포 수·비중, 상권 유형, 거리, 도달률로 목적 매출(로그)을 예측한 Ridge 5겹 교차적합값의 백분위
  - 공부는 매출 원천이 없어 PATH-v0 공급 점수로 대신한다
- U 성분과 가중치

| 성분 | v0 | v1 | 정의 |
|---|---:|---:|---|
| `u_resid` 저유입 잔차 | 0.30 | 0.45 | 관측 유입 − 구조 기대 유입. 음수일수록 높게 |
| `u_novelty` 새로움 | 0.20 | 0.20 | 직전 분기 총매출 역백분위 |
| `u_cat` 범주 거리 | 0.25 | 0.35 | 1 − 관성 Top-K와의 최대 코사인 유사도 |
| `u_spatial` 공간 거리 | 0.25 | 0 | 관성 Top-K까지의 거리 |

- MMR: `λ·S/max(S) − (1−λ)·max sim`, λ=0.7. sim은 범주 코사인과 `exp(−거리/1.5km)` 반반.

### 2.3 v0 → v1을 바꾼 이유
- v0의 공간 거리 항은 관성에서 멀수록 가점을 줬다. 관성(특히 거리순)이 출발지 옆에 몰려 있어서, 가까운데 안 가 본 곳이 감점됐다.
- 선행연구 검증 노트에서도 DISCOVERY 2024의 세렌디피티 모형이 오히려 가까운 POI를 선호했다고 나와 방향이 반대였다.
- 그래서 관성 이탈을 두 종류로 나눴다: 가까운데 안 가 본 곳, 멀지만 의외로 괜찮은 곳.

### 2.4 결과 예시
v0 식사 상위(동대문구 출발): 상계역, 동원전통종합시장, 수유역, 서울숲카페거리, 광운대역 1번.

v1 서울캠 출발 식사 구간별 1위:
| 구간 | 상권 | 이동 |
|---|---|---|
| 가까운데 안 가 본 곳(≤15분) | 태릉시장 특화거리 | 14분 추정 |
| 중간 거리(15~22분) | 청량리전통시장 | 16분 추정 |
| 멀지만 의외로 괜찮은 곳(22~30분) | 창신골목시장 | 24분 측정 |

- 이동시간: 서울캠은 ODsay 측정 60곳, 나머지는 측정값으로 맞춘 회귀(약 `3.31 × km + 8.8분`)다.

### 2.5 검증 (라벨 없이 한 것)
1. 시간 순 프록시 라벨 백테스트(2분기 자료로 순위 → 4분기 성장으로 판정). 평균 회귀에 오염돼 전 방법이 무작위 수준이었다. 성능 주장은 하지 않는다.
2. beyond-accuracy: 관성 겹침률, 지역구·상권 유형 수, ILD, 커버리지, 노출 지니.
   - 상권 유형 수 2.8은 거리순(3.0)보다 낮다.
   - ILD 0.257은 인기순(0.230)보다 높고 거리순(0.274)보다 낮다.
   - 평균 거리 5.4km. 인기순 7.2km보다 짧고 거리순 0.5km보다 길다.
3. 반사실 시뮬레이션: 동대문구발 비일상 유입의 5·10·20%가 Top-10으로 옮겨갈 때 유입 지니 변화.
4. 민감도: R 하한, λ, U 가중치, K. U 가중치가 결과를 가장 크게 흔든다.
5. 테스트 14개: 단조성, R 하한, 겹침률, MMR, 지니.

### 2.6 라벨 확보 계획
| 방법 | 내용 |
|---|---|
| Kotkov식 3문항 설문 | 의외성 5 + 관성 5를 섞어 보여 주고 ① 몰랐다 ② 예상 밖이다 ③ 가 보고 싶다를 5점 척도로 묻는다 |
| 팀원 블라인드 평가 | 문항 사전 검증용 |
| 유입 증가 사후 검증 | 지금 목록을 고정하고 다음 B078/B079 기간에 유입이 늘었는지 본다 |
| 캠퍼스 인지도 설문 연계 | 1장 한계 1번 설문에 같은 문항을 붙인다 |

라벨이 생기면: 로지스틱 회귀로 가중치 학습 → 라벨 1,000개 이상이면 LambdaRank → 조건부 로짓의 다양성 추구 항 → 밴딧·A/B.

### 2.7 남은 한계
1. 동대문구발 OD가 없다. `u_resid`와 과거 유입순은 행정동 배분 유입 프록시다. 그래서 이태원 같은 유명 상권이 가짜 저유입으로 잡혔고, 새로움 항으로 보완했다.
2. U 가중치는 사전 지정값이다.
3. U가 상권 단위라 같은 상권이 여러 목적에 뜬다.
4. 동대문구 출발 거리는 직선거리 근사다.

## 3. 의외성 선행연구 검증과 해설 (2026-11-02 ~ 11-03)

**한 일**
- 1차 검증 노트: 서지를 특정하고 초록 수준으로 판정했다. 원문 호스트가 막혀 "원문 확인"은 없다.

## 5. 리뷰 수집 방법 조사 (2026-11-03)

### 요약
**목적**: 네이버·카카오 리뷰를 모으는 방법과 선행 사례를 조사하고, 4장 점포 추천의 리뷰 항을 채울 수 있는지 본다.

**기준**: 대회 규정 원문에 리뷰 수집을 막는 조항이 없다는 팀 확인(11-03)을 따른다. 1장의 10-31 원칙("약관 위반 크롤링은 심사 제외")은 이것으로 대체됐다.

**결론**
- 네이버·카카오 모두 리뷰를 주는 공식 API가 없다.
- 카카오맵·네이버 지도 robots.txt는 모든 봇을 막고, AI 봇은 이름으로 지정해 막는다.

**상태**: 조사 완료. 공식 API 시범 수집은 키 발급과 도메인 허용을 기다린다.

| 직접 크롤링 (내부 요청) | 개발자도구 Network 탭에서 리뷰 요청을 찾아 `requests`로 직접 부른다. 빠르고 덜 깨진다. PyPI `naverplacescraper`(비상업용)가 있다 |
| 유료 도구 | Apify 액터(네이버 플레이스, 카카오맵), 크롬 확장(SellFit, 일퍼센트: 스마트스토어·쿠팡 최대 1,500건) |
| 판매자 도구 | 내 매장이면 스마트플레이스·스마트스토어·카카오 판매자센터 |
| 공식 API | 네이버 검색 API(블로그·카페 글 목록·요약), 카카오 로컬 API(장소 정보). 둘 다 리뷰 본문은 없다 |

- 카카오톡 선물하기 리뷰는 공개된 수집 사례가 없었다. 유료 구매평 광고가 많아 데이터 오염 위험이 있다.

### 5.2 관련 판례
| 사건 | 내용 |
|---|---|
| 야놀자 vs 여기어때 (대법원 2022.5.12. 2021도1533) | 공개 정보(숙박업소 이름·주소) 크롤링에 형사 무죄. 민사에서는 부정경쟁행위로 인정됐다는 보도가 있다(원문 미확인) |
| 잡코리아 vs 사람인 | 잡코리아를 DB 제작자로 인정했다는 언급만 확인(원문 미확인) |
| 네이버 부동산 DB 사건 (특허법원, 2026년 초) | 네이버 DB 제작자 지위 인정, 8,000만 원 배상 |

흐름: 소량 분석용은 비교적 안전하고, 대량 수집이나 경쟁 서비스 재게시는 위험하다. 리뷰 작성자 닉네임은 개인정보라 가명 처리가 필요하다.

### 5.3 mapjiri-datamining 저장소 검토
- 하는 일: "대전 + 행정동 + 메뉴"로 카카오맵을 검색한다. 1~3페이지 가게의 이름·주소·추천 포인트·리뷰 최대 50개를 Selenium으로 모은다. EventBridge → SQS → Lambda로 주기 실행한다.
- 판단: 설계(지역 × 메뉴 키워드 조합, 주기 실행)는 참고할 만하다. 코드는 그대로 쓰기 어렵다.
  - 절대 XPath와 옛 클래스명에 의존한다. 마지막 커밋이 2025-03이다.
  - 예외를 전부 삼켜 실패해도 빈 값이 나온다.
  - LICENSE 파일이 없다. 구조만 참고하고 코드는 새로 짜야 한다.

### 5.4 Selenium과 토큰
- Selenium: 실제 크롬을 코드로 조종하는 도구다. 이해하기 쉽지만 느리고 화면이 바뀌면 깨진다. 요즘은 Playwright를 더 많이 쓴다.
- 내 토큰(로그인 쿠키) 사용: 플레이스 리뷰는 공개 데이터라 로그인해도 받는 양이나 속도가 늘지 않는다. 대신 차단 단위가 계정까지 넓어져 계정 제한 위험이 생긴다. 쓸 이유가 없다.
- 카카오 REST API 키: 공식 API에 리뷰 기능이 없어 키가 있어도 리뷰를 받을 수 없다.

### 5.5 접근 정책 실측 (2026-11-03)
| 도메인 | robots.txt |
|---|---|
| `place.map.kakao.com`, `map.kakao.com` | GPTBot·ClaudeBot 등 AI 봇 9종 `Disallow: /`, `User-agent: *`도 `Disallow: /`(첫 화면만 허용) |
| `map.naver.com` | 같은 구조. 맨 위에 "AI 학습·RAG 목적 봇 접근 엄격히 금지" 문구 |
| `m.place.naver.com`, `pcmap.place.naver.com` | robots.txt 없음(앱 화면 반환). 두 번째 요청에 429 |

- 클라우드 세션에서 이 도메인들에 접속하려면 환경 설정의 Network access → Allowed domains에 추가해야 한다. 설정을 바꾼 뒤에도 안 되면 새 세션을 연다.
- Claude는 이 robots.txt가 이름으로 막은 AI라서, 리뷰 대량 수집을 Claude가 직접 돌리지 않기로 했다. 로컬 Claude 에이전트로 옮겨 돌리는 것도 같은 이유로 하지 않는다.

### 5.6 소요 시간 추정 (동대문구, 계산값)
가정: 음식점 약 3,200곳(숙박·음식점업 사업자 3,218곳 기준), 전체 점포 약 2만 곳(가정), 가게당 리뷰 평균 100개(가정), 요청 간격 1.5~2초.

| 방식 | 가게 1곳 | 음식점 3,200곳 | 전체 2만 곳 |
|---|---:|---:|---:|
| Selenium/Playwright | 약 25초 | 약 22시간 | 약 5.8일 |
| 내부 요청 직접 호출 | 약 8초 | 약 7시간 | 약 1.8일 |
| 공식 API 평판·키워드 방식 | - | 1시간 이내 | - |

- 위 값은 한 번도 막히지 않는다는 가정이다. 실측(4.7)으로 보면 네이버 플레이스는 캡차 토큰 없이는 첫 요청부터 막힌다. 그래서 크롤링 방식의 시간 추정은 현재 의미가 없다.
- 로그인 토큰을 써도 시간은 같고, 계정 위험만 커진다.

### 5.7 공식 API 대안 설계
1. 가게 목록: 카카오 로컬 API로 "지역 + 행정동 + 메뉴"를 검색해 가게명·주소·카테고리·좌표를 받는다.
2. 후기: 네이버 검색 API(블로그·카페)에 "가게명 + 지역"으로 검색해 제목·요약·링크·작성일을 받는다. 하루 한도는 제3자 자료 기준 2.5만 건이라 공식 문서 확인이 필요하다.
3. 리뷰 원문 일부: Google Places API가 장소당 최대 5개를 준다. 한국 가게는 구글 리뷰가 적고 저장 제한이 있다.
4. 분석: 협찬 글을 거르고("소정의 원고료", "제공받아"), 키워드 추출과 긍정·부정 분류로 가게별 평판 카드를 만든다.

| 원하는 결과 | 원문 없이 |
|---|---|
| 가게별 대표 키워드 | 가능 |
| 긍정·부정 비율 | 대체로 가능, 정밀도는 낮음 |
| 지역·메뉴별 비교 | 가능 |
| 메뉴별 세부 평가, 별점 | 어려움 |
| 시간에 따른 평판 변화 | 부분적 |

- 네이버 블로그 언급 수는 1장 현황 보고서가 제안한 '숨은 정도' 지표로도 쓸 수 있다.
