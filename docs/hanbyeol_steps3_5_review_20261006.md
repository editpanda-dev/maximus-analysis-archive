## 3. 공부 시설 접근성 v0의 정의

### S4와 중복 신호 제외

- 팀 결정대로 C_stay/S4는 제외한다. 검토 후보 427개는 여전히 unknown이며 학습 허용을 확인한 장소로 승격하지 않는다.
- 카카오 스터디카페 S3a를 공급 신호로 사용한다. 공식 독서실 S3b(`study_room_stores`)는 검증 열로 남기고 가중치를 더하지 않는다.
- 예전 75% 부분합을 그대로 최종 점수라고 부르지 않는다. 남은 가중치 비율 45:20:10을 75로 나눠 합계 1로 환산했다.

```text
공부 시설 접근성 v0 = 0.600000 × P(스터디카페 가중 집계)
                     + 0.266667 × P(공개 학습시설 가중 집계)
                     + 0.133333 × 대중교통 접근성 백분위

가중 집계 = 상권 내부 원천시설 수 + 0.25 × OSM 잠정 400m 외부 원천시설 수
```

`P`는 786개 상권의 해당 신호에서 **양수 값끼리** 동률 평균 백분위(0~100)를 계산한다. 집계 규칙상 0은 0점으로, 입력 결측은 결측으로 유지한다. 이 방식은 상대적 정렬 규칙이며 만족도 점수가 아니다. 접근성 백분위는 기존 334개 출발지/30분 분석의 입력을 그대로 사용하며 사용자 특정 출발지나 실시간 교통으로 해석하지 않는다.

시설 두 신호가 모두 0이면 총점은 NA이고 순위에서 제외한다. 여기서 0은 ‘이번 원천과 포함 규칙에서 0건’이다. 연결 미확보나 원천 미수집 때문에 실제 시설이 누락됐을 수 있으므로 시설 부재를 확정한 뜻은 아니다. 시설 없이 교통 접근성만으로 공부 상권을 추천하지 않는다.

### 상권 크기 보정 추가 진단

동일 690개에서 카페·공공시설 신호를 면적 밀도 또는 OLS 잔차로 대체하는 대안을 비교했다. 이는 v0 기본식을 조용히 바꾼 결과가 아니다.

| method | common_population | area_spearman | total_stores_spearman | top10_overlap_vs_count_v0 |
| --- | --- | --- | --- | --- |
| count_based_v0 | 690 | 0.322 | 0.371 | 1.000 |
| density_smoothed_0.05km2_diagnostic | 690 | -0.140 | 0.020 | 0.400 |
| OLS_log_count_residual_diagnostic | 690 | 0.021 | 0.023 | 0.800 |

밀도 대안은 `가중 시설 수 / (area_km2 + 0.05)`다. 잔차는 `log1p(가중 시설 수) ~ 1 + log(area_km2) + log1p(전체 점포 수)`를 같은 690개에 각각 적합해 잔차 백분위를 사용한다. 해당 시설 수 0인 성분은 0으로 고정한다. 두 대안 모두 교통 성분은 유지한다. 밀도 평활 0.05는 가정이다. 시설 원천이 서울 전체를 완전 수집한 자료가 아니므로 이 값을 ‘서울 평균 대비 특화도’로 부르지 않는다.

개수 기반 v0의 면적 상관 0.322가 남아 있으므로 **상권 크기 보정 후 시설 특화도를 확정한 최종 추천**으로 표현하지 않는다. 잔차 대안은 면적 상관 0.021·Top10 유지율 80%로 비교적 안정적이지만 이번 제출에서는 진단으로 남긴다. 목적 점수의 채택 방식 합의 후 별도 버전으로 적용할 수 있다.

## 4. 세 목적의 접근성 정의 검토 및 공통 대안

### 실제로 확인한 문제

김건우님 최신 코드에는 `--walk-routes`와 보행망 계산 절차가 추가돼 있다. 하지만 제출된 786행 `walk_distance_basis`와 QA는 **전부 euclidean_400m_buffer**다. 코드가 있다는 사실만으로 이미 보행 결과가 적용됐다고 간주하지 않았다. 코드의 경로 누락 처리에는 직선거리 fallback도 있어, 캐시 적용 후에도 정의 혼합 여부를 점검해야 한다.

카페 초안은 공식 상권 내부 점포·매출을 사용하고 외부 POI 보행 반경을 점수에 더하지 않는다. 공부 v0는 내부+OSM 잠정 외부400m를 사용한다. 따라서 세 기존 점수를 바로 평균해 ‘동일 보행 정의의 최종 조합’으로 발표할 수 없다.

### 수행한 공통 내부 공급 비교안

- 동일 공식 폴리곤의 **내부만** 포함한다. 모든 외부 시설을 제외하며 내부 거리는 집계 규칙상 0m다.
- 식사: 김건우님 최신 `food_inside_count` 사용. 제과점/카페/주점 제외 매핑은 최신 코드에서 확인.
- 카페: 커피·음료+제과점 공식 내부 점포 수 사용.
- 공부: 이번 후보쌍의 내부 스터디카페·공개 학습시설만 사용. S4/S3b/외부 연결은 제외.
- 세 목적 모두 동일 `area_km2 + 0.05` 밀도 분모 사용. 목적별 양수 밀도를 백분위로 변환하고 공부 공급은 45:20을 65로 나눠 결합한다.
- 조합에 포함되는 동일 상권 집단에서 각 목적 점수를 다시 백분위로 변환한 뒤 동등 평균한다. 결측 목적 점수를 평균에서 빼고 나머지만 평균하지 않는다.
- 이 비교안은 **공급만** 비교한다. 매출 관측군/추정군을 섞은 기존 full score가 아니며, 내부 집계가 실제 출입구 검증을 의미하지 않는다.
- 식사 2026-06 SBIZ·카페 2025Q4 공식 점포·공부 2026-09 POI의 시점·수집범위 차이는 남아 있다. 공간 기준만 통일한 탐색 진단이다.

식사+카페+공부 내부 공급 공통 집단은 **258개**다. 카페+공부 내부 공급 비교도 현재 258개에서 산출됐다. 이 숫자는 카페 완전관측 218개나 과거 3목적 탐색 208개와 다른 조건의 집단이다.

## 8. 1·2번 Git 원격 공유 실패 원인과 실행 가능한 대안

일반 `git push`는 `could not read Username for https://github.com`으로 실패했다. 현재 실행 환경에 Git HTTPS 쓰기 인증이 없다. 연결 GitHub의 저장소 metadata는 pull/push=true였지만 실제 작업 브랜치 생성 호출은 **HTTP403 Resource not accessible by integration**으로 실패했다. 별도 API를 반복하거나 main을 강제 갱신하지 않았다. 원격 branch 생성과 commit 반영은 완료되지 않았다.

### repository owner가 할 일

- 연결 GitHub App 설치에서 이 저장소가 포함돼 있는지, **Contents: Read and write** 권한이 승인돼 있는지 확인/갱신한다. 메타데이터의 push=true만으로 앱 쓰기가 실제 허용된다고 보장하지 않는다.
- 조직/저장소의 브랜치 생성 정책과 연결 계정의 write 권한도 확인한다. 정확한 403 원인 판별에는 소유자의 설치 권한·정책 확인이 필요하다.
- 권한 갱신 후 작업 브랜치 생성·파일 반영을 다시 확인한다. API 키와 이 GitHub 쓰기 권한은 별개다. 카카오 키를 Git 인증에 사용하지 않는다.

### 사용자 Windows에서 1·2번 커밋을 공유하는 방법

ZIP에 `maximus_steps1_2_1a69e28.bundle`을 넣었다. 이는 커밋 내역을 보존한 Git 전송 파일이며 1·2번까지의 정확한 HEAD는 `1a69e28763f84792eaf4354597751d3849fb4c3e`다. 작업 폴더의 ZIP을 다시 commit하는 방식과 다르다. 아래는 압축을 `C:\work_maximus\maximus_steps3_5_delivery`에 풀었다는 기준이다.

새 clone 폴더 이름이 이미 있으면 기존 폴더에 덮어쓰지 말고 다른 이름을 사용한다.

```powershell
cd C:\work_maximus
git clone https://github.com/editpanda-dev/maximus-analysis-archive.git maximus_analysis_share
cd C:\work_maximus\maximus_analysis_share
git fetch origin codex/integrate-study-public-facilities
git bundle verify C:\work_maximus\maximus_steps3_5_delivery\maximus_steps1_2_1a69e28.bundle
git fetch C:\work_maximus\maximus_steps3_5_delivery\maximus_steps1_2_1a69e28.bundle "refs/heads/codex/hanbyeol/cafe-study-taxonomy-20260929:refs/heads/codex/hanbyeol/cafe-study-taxonomy-20260929"
git log -1 codex/hanbyeol/cafe-study-taxonomy-20260929
git push -u origin codex/hanbyeol/cafe-study-taxonomy-20260929
```

`git log -1`에서 1a69e28인지 확인한다. 로그인 창이 나타나면 저장소 write 권한 있는 GitHub 계정으로 로그인한다. 기존 원격에 다른 커밋이 먼저 생겨 push가 거절되면 `--force`로 덮어쓰지 말고 결과를 공유해 충돌을 검토한다. 이 절차는 사용자가 성공 로그를 전달하거나 원격 조회가 확인돼야 공유 완료로 판정한다.

`maximus_steps3_5.bundle`은 이번 수정까지 포함한 별도 전달본이다. 위 명령은 요청한 1·2번만 먼저 공유하기 위해 1a69e28 bundle을 사용한다. 이번 실행과 무관한 교통 원천 ZIP 변경, API 키, .env, .venv는 commit/bundle에 추가하지 않았다.
